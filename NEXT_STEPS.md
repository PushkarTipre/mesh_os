# MeshOS — Next Steps

Where things stand: **Checkpoints 0–9 are done in code** (see [ROADMAP.md](ROADMAP.md) for what each one covers). This file is the actual to-do list from here — what's genuinely outstanding, ordered by priority, plus what's deliberately *not* planned and why.

This is a private project (see README.md's "Release status") — nothing here assumes or leads toward a public release.

## Priority 1: Hardware verification

This is the real remaining work. Every checkpoint's protocol logic is proven against simulated transports (134 tests across `mesh_core`/`mesh_os`/`mesh_console`, zero hardware), but **none of it has run on an actual phone**. `FakeTransport` proves the logic is correct; it can't prove `NearbyTransport`/`BleTransport` actually talk to real radios correctly, or that the on-device UX holds up. Until this happens, treat every checkpoint as "should work" rather than "works."

Needed: 2 Android phones with Google Play services minimum, a 3rd for anything multi-hop (CP6+), Bluetooth on both for CP8.

Work through these in order — each depends on the identity/session/trust plumbing the previous ones exercise:

- [ ] **CP3–CP5**: install on two phones, confirm auto-discovery/connect/handshake, send messages both directions, do the QR trust exchange, block/unblock, force-quit and confirm identity + chat history + trust survive restart. (README.md "Try it," steps under "CP3–CP5 demo.")
- [ ] **CP6**: bring in a 3rd phone, confirm multi-hop delivery through a relay that never sees plaintext, and store-and-forward when the destination is temporarily offline.
- [ ] **CP7**: confirm a broadcast reaches phones with no prior contact; send a real photo with file transfer, and specifically force an interruption (walk out of range mid-transfer) to confirm it pauses and resumes instead of corrupting or restarting.
- [ ] **CP8**: disable Nearby specifically on one phone (not just airplane mode — needs to isolate "no Nearby" from "no radio at all") and confirm `MultiTransport` actually falls back to BLE, not that Nearby was secretly still working. Time a large transfer both ways to confirm Nearby is actually faster when both are available.
- [ ] **CP9**: watch the debug view's counters move live during ordinary use; hand the README to someone who hasn't touched this codebase and see if they get two phones talking in under 30 minutes without help.

If any of these fail, that's expected to surface real bugs — the simulated tests can't catch radio-specific issues (real MTU negotiation, real advertising payload limits, real Android permission dialogs, timing under actual Bluetooth/Wi-Fi latency). Fix what breaks, add regression tests where the fix is expressible in `FakeTransport` terms, and note in ROADMAP.md what was hardware-specific.

**No second device yet?** The **Mesh Simulator** screen in `mesh_console` (drawer → "Mesh Simulator", `apps/mesh_console/lib/mesh_simulator_screen.dart`) runs a real 3-node mesh in-process on one device/emulator, using the actual `MeshLink`/`FileTransferManager` code over an in-memory fake radio -- see README.md's "Try it." It's real evidence the protocol stack works correctly compiled into a running app, and it's the thing to reach for first if something seems broken (it'll tell you whether the bug is in the protocol logic or specifically in the transport/radio layer). It is **not a substitute for the checklist above** — it structurally cannot exercise `NearbyTransport`/`BleTransport` themselves, since that requires two real radios in range of each other.

**Cross-device reliability (in progress):** works on a Samsung S24 Ultra; a OnePlus Nord initially showed the home screen's loading spinner sticking for about a minute before the app crashed. The on-device error log (added specifically to debug this -- see below) caught the real sequence on a second attempt: `BlePermissions.requestAll()` (`packages/mesh_transport_ble/lib/src/ble_permissions.dart`) genuinely never authorizes on this device -- both the central and peripheral `authorize()` calls ran out their full 10s timeout (20s total) and came back denied, every launch. The app used to construct and run `BleTransport` regardless of that outcome; running BLE scanning without OS authorization appears to silently drop its service-UUID filter on this device, so *every* BLE peripheral in range (headphones, laptops, whatever else was nearby) showed up in "Nearby devices" as if it were a MeshOS peer. `MeshOS` auto-connects to everything it discovers, so each of those became a real GATT connection attempt against a device that was never going to have the MeshOS service -- failed, and the failure-path disconnect call itself threw an uncaught `PlatformException` (`IllegalStateException: Disconnect failed with status: 22`) that crashed the app a few minutes in. **Fixed:** `MeshOS.start()` (`packages/mesh_os/lib/src/mesh_os.dart`) now only constructs `BleTransport` when `bleGranted` is actually true -- an unauthorized radio is never driven at all. `BleTransport`'s three fire-and-forget disconnect/respond calls (`packages/mesh_transport_ble/lib/src/ble_transport.dart`) also now swallow their own errors as defense in depth, regardless of the permission state. Two smaller bugs found along the way, also fixed: `mesh_console`'s `MeshDebugScreen`/`BroadcastScreen` could crash or silently no-op if opened before `start()` finished; and the QR "My Identity Card" screen forced re-typing the display name on every visit instead of remembering the last one used.

Still unconfirmed after this fix: a stuck store-and-forward count (`storedRelayPackets` nonzero for two devices sitting next to each other). This was reported from the same test session as the BLE churn/crash above, so it's plausibly downstream of an unstable Bluetooth radio (Nearby's own discovery also rides on BLE) rather than a separate bug -- but that's a hypothesis, not yet confirmed. Retest with the BLE fix in place; if it persists with a clean (no rogue-BLE) startup, it's a real bug in the routing layer and needs its own investigation with fresh `MeshOS.diagnostics`/`MeshLinkStats` data.

**Two nearby phones showing "not nearby" after backgrounding, screen-off, or even a full app restart (fixed) -- discovery never resumed itself.** Android suspends or heavily throttles both Nearby Connections and BLE scanning/advertising while an app is backgrounded (most aggressively once the screen turns off), and neither radio automatically resumes just because the app becomes visible again -- and `mesh_console` had zero app-lifecycle handling at all, so nothing ever told it to restart discovery. Once a device's connection-attempt tracking got marked "already tried" before backgrounding cut off event delivery, it also had no way to clear itself, since the `disconnected` event that would normally do that never had a chance to fire. Fixed with `MeshOS.refreshDiscovery()` (`packages/mesh_os/lib/src/mesh_os.dart`): stops and restarts advertising/discovery and clears that stale tracking. `mesh_console`'s `HomeScreen` (`apps/mesh_console/lib/main.dart`) now mixes in `WidgetsBindingObserver` and calls it on every `AppLifecycleState.resumed`, so returning to the app -- from the background, from screen-off, or from the recents switcher -- always re-announces this device and re-scans for others, instead of assuming a scan session from before backgrounding is still alive.

**A message/broadcast "delivered" without the recipient ever seeing it (fixed) -- root cause was app-level, not protocol-level.** `ChatScreen`/`BroadcastScreen` each held their own `mesh.messages` listener and their own in-memory message list, built only while that specific screen was the one on top. `mesh.messages` is a broadcast stream with no replay buffer -- a message arriving while nobody happened to be listening (recipient on the home screen, on a different peer's chat, or on the broadcast screen showing someone else's) was dropped outright, permanently, the instant it arrived. Meanwhile `mesh_core`'s session layer had already ACKed the packet before the app layer ever saw it, which is exactly why the *sender* still saw "delivered" -- that status was accurate at the protocol level the whole time; the app just threw the content away afterward. Fixed by moving persistence out of the per-screen listeners entirely: `ChatHistoryStore` (`apps/mesh_console/lib/chat_history.dart`) and the new `BroadcastLog` (`apps/mesh_console/lib/broadcast_log.dart`) are now shared, live-updating stores fed by a single listener owned by `HomeScreen` -- alive for as long as the app is in the foreground, independent of which screen (if any) is on top. `ChatScreen`/`BroadcastScreen` now just render whatever's already in the shared store and subscribe to its `updates` stream for live refresh while open.

**Long startup delay on every launch, not just the first (fixed) -- BLE's permission check was hanging out its own timeout every single time.** Once BLE permission is granted (or denied) on a device, that outcome is fixed -- there's nothing left to ask. But the `bluetooth_low_energy` plugin's `authorize()` unconditionally calls Android's `requestPermissions` and waits for a result callback that, per the earlier crash investigation, never fires once there's nothing new to prompt for. `BlePermissions._authorize` was already bounded by a 10s-per-call timeout so this couldn't hang forever, but that meant every launch paid up to 20s (central + peripheral) for a question the OS had already answered. Fixed in `packages/mesh_transport_ble/lib/src/ble_permissions.dart`: check `CentralManager()`/`PeripheralManager()`'s `.state` first -- a cheap, already-cached value the plugin itself keeps fresh via a plain status query (not a request-and-wait flow) -- and only fall through to the slow `authorize()` when that state is genuinely undetermined, which in practice means the first launch ever. Combined with the earlier fix that runs Nearby's and BLE's permission requests concurrently (`MeshOS.start()`), a repeat launch should no longer pay either cost.

**App killed or long-backgrounded: still a real, separate limitation, not covered by the fix above.** The fix above covers "any screen, as long as the process is alive" -- which is most of what "backgrounded" means in practice, since Android usually keeps a minimized app's process alive for a while. It does **not** cover the process actually being killed (swiped from recents, or force-stopped by the OS under memory pressure) -- once that happens, nothing Dart-level can react to incoming data, because there's no running code left to react with. Receiving mesh traffic while fully backgrounded or after being killed needs a persistent Android foreground service (with its own mandatory ongoing notification, plus likely a battery-optimization exemption prompt, since OEM skins -- OxygenOS in particular, per the crash investigation above -- are aggressive about killing background radios regardless). This is exactly the "Background operation" item already listed under Priority 3 below -- a real, scoped v2 feature, not a quick fix, and worth a deliberate decision on scope/UX before starting rather than folding into a bug-fix round.

**Startup timeout was a dead end (fixed).** The 45s timeout added to catch a hang instead surfaced a new bug: on the OnePlus Nord, `start()` legitimately (not a hang) took a bit over 45s -- 5 Android runtime permission dialogs plus BLE's own up-to-20s authorize() timeout, requested sequentially, comfortably exceeds that budget even when everything works. `HomeScreen._bootstrap()` used `.timeout()`, which stops *waiting* on the deadline but doesn't stop `start()` itself -- so it kept running, logged its own success a few seconds later, and the UI never found out, stuck on a permanent "Failed to start" screen despite the mesh actually being up. Fixed two ways: `MeshOS.start()` now requests Nearby and BLE permissions concurrently (`Future.wait`) instead of sequentially, cutting worst-case wall time roughly in half, and `NearbyPermissions.requestAll()` got the same defensive timeout-then-false pattern `BlePermissions` already had. More importantly, `_bootstrap()` no longer abandons `start()`'s result at all -- it always awaits the real outcome, showing a non-fatal "still starting" hint after 20s instead of a dead-end error, so a slow-but-successful start now just looks slow, not broken.

To debug without needing `adb` or a second computer at all, `mesh_console` now has on-device diagnostics: `MeshOS.diagnostics` (ARCHITECTURE.md §10), a persistent cross-restart `AppLog` (`apps/mesh_console/lib/app_log.dart`) capturing every diagnostic step plus all uncaught Dart/Flutter errors, and an `ErrorLogScreen` to view/copy/clear it (drawer → "Error Log"). This is what surfaced the crash stack trace above.

## Priority 2: Known limitations worth revisiting after hardware testing

These are documented (ARCHITECTURE.md, SECURITY.md) as accepted v1 trade-offs, not bugs — but hardware testing may reveal some matter more than expected:

- [ ] **BLE legacy advertising byte budget** (ARCHITECTURE.md §11): a full 128-bit service UUID plus the advertised name may not fit in a 31-byte legacy advertising packet on older chipsets. Unverified without hardware — if CP8 testing shows truncation, the fix is likely dropping to a shorter service-scoping scheme or leaning on extended advertising exclusively.
- [ ] **Relay store and file-transfer state are in-memory only** (ARCHITECTURE.md §7): an app restart mid-relay or mid-transfer loses that state. Low priority unless real usage shows this actually happens often enough to matter.
- [ ] **`MultiTransport.maxPayloadSize`** is the minimum across transports (correctness over efficiency) — fine unless real throughput testing shows this meaningfully hurts Nearby's performance in practice.

## Priority 3: Post-1.0 features (not started, no scoping done yet)

From ROADMAP.md's "Deferred" list — these are real future directions, not committed to a specific checkpoint order. Sequencing them is itself a future decision.

- [ ] **iOS support** — BLE GATT interop via the existing `mesh_transport_ble` design (the `Transport` interface was kept clean for this), or `MultipeerConnectivity` as an iOS-native alternative. Biggest single undertaking on this list; effectively re-runs CP3/CP8's transport work for a second platform.
- [ ] **Background operation** — foreground service on Android first (v1 is foreground-only by explicit scope decision), iOS background modes later. Needed for MeshOS to be useful as "always-on" infrastructure rather than only while the app is open.
- [ ] **Smarter routing** — the staged path from ARCHITECTURE.md §7's table: flooding (done, v1) → breadth-first/probabilistic gossip → distance vector → AODV → adaptive routing on historical encounter graphs. Each step trades implementation complexity for less wasted relay bandwidth. Worth revisiting once real mesh sizes/densities are known from actual usage — premature to build v2 routing against guessed traffic patterns.
- [ ] **CRDT sync** — conflict-free replicated data types for offline-first shared state (beyond simple message passing) — e.g. shared documents, collaborative lists. A genuinely new subsystem, not an extension of existing messaging.
- [ ] **Internet bridge nodes** — a node with real internet connectivity relaying mesh traffic to/from the wider internet. Raises new trust/security questions (a bridge node sees traffic patterns no purely offline relay would) that need real design work, not just implementation.
- [ ] **Desktop support** — would need its own transport work (different Bluetooth/Wi-Fi APIs per desktop OS) and UI adaptation; no groundwork laid yet.
- [ ] **Custom transport plugin API** — right now, adding a transport means implementing `Transport` and wiring it into `MultiTransport` by hand inside `mesh_os`. A real plugin API would mean a stable, documented, externally-implementable interface with its own versioning guarantees — worth doing once there's a second real consumer of `Transport` beyond Nearby/BLE to design against.
- [ ] **Developer dashboard** — a proper topology/analytics tool beyond `mesh_console`'s intentionally-plain debug screen (CP9). Only worth building once there's an actual need driving specific requirements (what would you want to see, that the debug view doesn't show?).

## Explicitly not planned

- **Publishing to pub.dev.** Decided against — this stays a private project, consumed via path dependency within this workspace (or `git:` if it's ever split across repos). Pub.dev's entire value is letting people *outside* this repo add the package with one line instead of pointing at source directly; with no intended external consumer, it adds nothing. See README.md's "Release status."
- **Open-source release / public repo.** Same reasoning — not applicable to a private project.
- **LICENSE file.** Only matters once (if ever) code leaves this repo's control — e.g. if you later share it with a collaborator, contractor, or another project outside your own ownership. Not needed for solo private use. Worth a five-minute decision *if* that situation ever comes up, not before.
